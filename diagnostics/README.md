# Registration failure recovery: evidence and operational guidance

## Short version

`MarshmallowPlugin.schema_helper` records a schema name in
`OpenAPIConverter.refs` before converting the schema. If conversion raises,
`refs` keeps a name that has no matching entry in `Components.schemas`. A
retry with the same `APISpec` then treats the schema as already converted and
emits a `$ref` to a component that was never registered.

The same pre-conversion write lets a restricted projection
(`Nested(ProductSchema, only=...)`) claim the parent's canonical name while the
parent registration is in progress.

The patch makes the reference write transactional and reserves in-flight
component names. It preserves the naming rule in `common.resolver`: a schema
still derives its name from its class, minus a trailing `Schema`.

## Minimal reproduction

Executable sample: `diagnostics/registration_failure_repro.py`. It installs a
local `MarshmallowPlugin` attribute hook and makes no network requests.

The model graph is circular:

- `ProductSchema` has `part = Nested(PartSchema)`.
- `PartSchema` has `product = Nested(ProductSchema, only=("id", "name"))`.
- `ProductSchema` also has `secret = ExplodingField()`.
- The hook deterministically raises `RuntimeError` while converting
  `ExplodingField`.

The harness covers two field orders:

1. **Failure after the part is registered** (`part` before `secret`). `Part` and
   the restricted `Product` projection are already committed when the leaf
   fails.
2. **Failure before the part is registered** (`secret` before `part`). Only the
   failed `Product` name is left in `refs`.

A separate **declared-projection control** uses an intentionally
over-restricted schema (`only=("id",)`) and never raises. It distinguishes a
bad declaration from a failure cache.

Evidence files (generated by running the harness against baseline and patched
source, respectively):

- `diagnostics/registration_failure_evidence.baseline.json`
- `diagnostics/registration_failure_evidence.patched.json`

## Causal evidence

### Failure before the nested part is registered

Baseline, immediately after `Product` failed:

```text
components.schemas: ["Health"]
converter.refs:     ProductLeafFirst -> ProductLeafFirst
                     ProductLeafFirst is NOT in components.schemas
```

Retrying the same `APISpec` after fixing the leaf produced a path but no schema:

```text
components.schemas: ["Health"]
paths:              ["/health", "/products"]
unresolved $refs:   ["#/components/schemas/ProductLeafFirst"]
```

The new path contains `$ref: #/components/schemas/ProductLeafFirst`; the
component does not exist. The only remaining record is the stale `refs` entry.
The healthy `/health` operation remains usable, showing the failure is
localized to the failed schema's registry entry.

Patched, after the same failure: `refs` is empty for the failed schema, and the
retry registers both `ProductLeafFirst` and `PartLeafFirst` with no unresolved
refs. Same-instance and fresh-instance retries now produce the same fields.

### Failure after the nested part is registered

Baseline, immediately after the leaf failed:

```text
components.schemas: ["Health", "Product", "Part"]
Product properties: ["id", "name"]
converter.refs:
  ProductSchema (canonical)          -> Product
  PartSchema                         -> Part
  ProductSchema only=("id", "name")  -> Product   # same name!
```

The canonical `Product` key was written first, but conversion failed. The
restricted projection then resolved to the same default name and registered
`Product` with only `id` and `name`. Retrying the same instance skipped
conversion because the canonical key was already in `refs`:

```text
same-instance retry: Product properties ["id", "name"]
fresh instance:      Product properties ["id", "name", "part", "secret"]
```

The two retries did **not** yield the same extracted fields. The same-instance
retry reused the projection that had claimed the name; the fresh instance
re-converted the full schema.

Patched, the restricted projection is registered as `Product1` because
`Product` is reserved while the parent converts. The canonical `Product` keeps
`id`, `name`, `part`, and `secret`. Same-instance and fresh-instance retries now
match.

### Declared-projection control (no error)

The control raises nothing. Both baseline and patched runs produce:

```text
components.schemas: ["DeclaredProduct", "DeclaredPart"]
DeclaredProduct properties: ["id"]          # deliberate restriction
DeclaredProductSchema only=("id",) -> DeclaredProduct
direct conversion of DeclaredProductSchema: ["id", "name", "part"]
```

A same-instance rerun and a second fresh run produce the same result. This is a
genuinely wrong or over-restricted declaration, not a stale failure cache: it is
deterministic and repeatable. The correct response is to fix the declaration,
not to clear the instance.

### Projection/name collision control

There is a second, related baseline bug that does not require an exception.
Entering through `PartSchema` with a restricted `Product` projection elsewhere:

```text
baseline, product-first entry: Product properties ["id", "name", "part", "secret"]
baseline, part-first entry:    Product properties ["id", "name"]
converter.refs (part-first):   ProductSchema only=("id","name") -> Product
```

The order determines whether the canonical or restricted schema wins the name.
The patch reserves the parent name and keeps both:

```text
patched, product-first entry: Product1 (restricted) and Product (canonical)
patched, part-first entry:    Product (restricted) only
```

Part-first entry is a legitimate use of a restricted projection when the parent
is never registered; no canonical definition exists in that run. Product-first
entry now preserves both definitions instead of silently overwriting one. The
naming rule is unchanged: both names originate from `ProductSchema`, and the
existing numeric suffix policy resolves collisions.

## Operational rules for the ingestion job

### Safe to reuse the instance when

1. Every value in `converter.refs` is also a key in `components.schemas`.
2. The generated document has no `$ref` whose target is missing.
3. Components known healthy before the failure (for example `Health`) are
   still present.

The patched library enforces rule 1 for failures during marshmallow schema
conversion and leaves already-registered components intact. While rule 1 holds,
reuse and retry are safe.

### Stop and use a fresh instance when

Observe any of these on the failed instance:

- a value in `converter.refs` is missing from `components.schemas`;
- the document contains a `$ref` to a missing component;
- a schema's extracted fields are a strict subset of the expected fields and
  match an `only`/`exclude` projection rather than the full schema;
- the expected canonical schema was replaced by a restricted projection.

With the baseline code, the failure-before-part case leaves a stale
`ProductLeafFirst` entry; the failure-after-part case leaves a stable but
restricted `Product`. Neither should be reused. Start a fresh instance, or
upgrade to the patched version and re-run the registration from the beginning.

## Verification

```text
.venv/bin/python diagnostics/registration_failure_repro.py
.venv/bin/pytest tests/test_ext_marshmallow.py::TestRegistrationFailureRecovery
.venv/bin/pytest tests/test_ext_marshmallow_common.py::TestUniqueName
.venv/bin/pytest
```

The failure-recovery regression cases fail on the baseline source and pass with
the patch. The declared-projection control behaves identically before and after
the patch, which is the point: it is a declaration problem, not a cache problem.
